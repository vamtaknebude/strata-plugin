# Decision Review and Learning

Use this reference after Uprali output identifies the exact current values and current organization context needed for the requested action. If the user supplies a visible Assumption Review, Decision, Outcome Review, Outcome Review Revision, or Decision Learning ID and the requested write does not require case identifiers, perform the matching protected read before resolving a case. Each activity is optional unless the user asks for it or its product prerequisite is needed for the next requested record.

Any Organization member with current required access may perform any human action. Do not invent job titles, workflow roles, handoffs, or separation of duties. Record approval steps only with the approval tools that the approvals reference names, and only when they are available. An approval path never blocks or changes a Decision. Several members may contribute without changing tool inputs. The server records the authenticated acting member.

## Concepts

- Assumption Review evaluates one exact active Assumption Revision against its complete ordered Evidence Link set. It never reviews partial Evidence, unrelated Case Evidence, external research, implicit organizational knowledge, or new web content.
- Attempt is one execution try inside a Review. A request or retry returns queued Attempt status. A terminal Attempt is one of failed, no material Findings, or Findings.
- Finding is advisory. It states one concern and why it matters. It cites one to five exact input Evidence Items. It has no severity, category, replacement text, or Decision recommendation.
- Finding Disposition records an accept or reject judgment and rationale for one Finding. A correction appends a successor Disposition with predecessor, correction reason, actor, and time. It does not edit the Assumption.
- Decision is immutable. It pins one exact Case Revision, one outcome, rationale, optional Conditions and disagreements, one selected Option Revision for approve or pilot, optional same-revision Scenario Revision, and complete Outcome Commitments when required.
- Outcome Commitment states the expected result, evaluation period, review date, planned Evidence source, action criteria, and accountable member.
- Outcome Review Revision is an authored Review snapshot for one Decision and assessment date. It contains the complete authored Observation set for that Revision. A draft may omit due Observations until completion. It may contain zero or more Decision Learnings.
- Observation belongs to one Outcome Review Revision. Correcting any Observation creates a successor Review Revision with the complete corrected Observation set.
- Decision Learning becomes accepted only when its exact Outcome Review Revision is completed. Accepted Learning content is immutable.
- Learning retirement appends a retirement fact for an accepted Learning that is not already retired or superseded.
- Exact Learning references are authored on a successor Case Revision or before Template Revision publication. They are explicit reuse facts, not search results or recommendations.

## Read Before Write

Before any state-changing operation, perform a fresh protected read that establishes the expected current state and all exact identifiers the write requires. Show one complete preview of the exact normalized input and expected effect. Wait for explicit confirmation tied to that preview. Generate a fresh version 4 UUID idempotency key only after confirmation.

Do not use a historic read as current state. Do not reuse an idempotency key for a different confirmed command. Do not call a later planned mutation after an earlier mutation fails in the same turn.

All capability calls use redacted argument audit. Read success audit belongs to the capability runtime. Write success audit belongs to the domain transaction. Do not expose audit internals, provider metadata, prompts, tokens, hidden identifiers, or protected content metadata.

Every write capability must return fallback text that lets the user understand the result without reading structured JSON. Use resource links only when the capability returns them. Otherwise state that no resource links were returned. Assumption Review writes expose `INPUT_INVALID`, `COMMAND_REUSED`, `STALE_STATE`, and `RESOURCE_UNAVAILABLE`. Decision and Outcome Review writes expose nondisclosing `CASE_NOT_FOUND` for missing or inaccessible protected facts. Case Learning reference revision returns `RESOURCE_UNAVAILABLE` for a missing or inaccessible target Case, source Case, or Learning. It returns `STALE_STATE` for a noncurrent Case head, a closed Decision Cycle, or an ineligible Learning, and also exposes `COMMAND_REUSED` and `INPUT_INVALID`. Template Learning publication retains `RESOURCE_UNAVAILABLE` for missing or inaccessible Template Publication facts.

`COMMAND_REUSED` means the same key was already used with different normalized input. Stop, perform the required fresh read, show a complete new preview, obtain new confirmation, and use a new key.

`STALE_STATE` means the expected current state is no longer current. Read the exact current protected state, compare it with the confirmed proposal, show a complete changed preview, obtain new confirmation, and use a new key.

For Decision and Outcome/Learning reads and writes, nondisclosure uses `CASE_NOT_FOUND` for missing or inaccessible protected facts. Assumption Review `RESOURCE_UNAVAILABLE` means a required Review input is missing or inaccessible. Provider failures appear as `failureCode` on a terminal failed Attempt. Template Learning publication uses `RESOURCE_UNAVAILABLE` for missing or inaccessible Template Publication or Learning facts. Do not infer whether a protected fact exists, name hidden relationships, ask Uprali to disclose subsets, or try alternate identifiers to discover restricted content.

A lost response, timeout, or ambiguous transport result permits at most one same-key retry with byte-identical normalized input. Same-key same-input replay returns the original receipt. This rule applies only to that ambiguous command.

## Assumption Review

Use `strata_request_assumption_review` to request one Review of one exact active Assumption Revision. Input: `assumptionRevisionId`, `expectedCaseRevisionId`, and `idempotencyKey`. Effect: open-world idempotent write that queues provider execution after the request commits. Output: `reviewId`, `attemptId`, `attemptNumber`, `assumptionRevisionId`, and `replayed`. Resource links are not returned.

Use `strata_read_assumption_review` to poll or inspect a Review. Input references either a `reviewId` or an `assumptionRevisionId`; include `limit` and returned cursors only for the same reference. Top-level `limit` is from 1 through 20 and defaults to 20; this is distinct from the case-projection maximum of 25. Preserve the same top-level `limit` when continuing with `cursor`. Output is a protected bounded projection with `freshness`, Attempt states, Findings, current Dispositions, optional Disposition history, and opaque context-bound cursors. A failed Attempt's `attemptId` maps to `expectedLatestAttemptId`; its `resultId` maps to `expectedFailedResultId`. Use both only for an explicitly confirmed retry. Provider, model, token, duration, prompt, and protected content metadata are omitted.

Poll a queued or running Review at most three times over at most 30 seconds unless the user explicitly asks to wait longer before polling starts. Stop when an Attempt becomes failed, no material Findings, or Findings, or when the bound is reached. Failed Attempts are never no-material-Findings results. Timeout, refusal, malformed output, invalid citation, cancellation, resource unavailability, configuration failure, executor unavailability, provider unavailability, or read failure never means no material Findings.

Use `strata_retry_assumption_review` only when the user explicitly confirms retry of the current latest failed Attempt. Input: `reviewId`, `expectedLatestAttemptId`, `expectedFailedResultId`, and `idempotencyKey`. Effect: open-world idempotent write that queues one new Attempt. Output: `reviewId`, `attemptId`, `attemptNumber`, `assumptionRevisionId`, and `replayed`. Do not automatically retry. Do not retry a completed or superseded Review. A non-current Attempt, non-failed Attempt, mismatched failed Result, completed Review, or superseded Review returns `STALE_STATE`.

Use `strata_save_finding_disposition` to accept or reject one Finding. Input: `findingId`, `disposition`, `rationale`, `expectedCurrentDispositionId`, `correctionReason`, and `idempotencyKey`. Effect: closed-world idempotent write that appends the current Disposition or its correction without editing the Finding. For a first Disposition, send `expectedCurrentDispositionId: null` and `correctionReason: null`. For a correction, send both the current Disposition ID and a nonblank correction reason. Output: `dispositionId`, `predecessorDispositionId`, `findingId`, `reviewId`, and `replayed`.

## Decision

Use `strata_create_decision` after a fresh read of the exact current Case Revision. Input includes `investmentCaseId`, `decisionCycleId`, `caseRevisionId`, `expectedCaseRevisionId`, `outcome`, `rationale`, `selectedOptionRevisionId`, `selectedScenarioRevisionId`, `calculation`, `conditions`, `disagreements`, `commitments`, and `idempotencyKey`. Effect: closed-world idempotent write. Output: `decisionId`, `investmentCaseId`, `decisionCycleId`, `caseRevisionId`, `decidedAt`, and `replayed`. Resource links are optional.

For a calculated Decision, preserve the exact Run the user chose from structured creation output in this conversation or from a visible retained Run. A creation receipt with `status: "created"` does not establish that the Run succeeded. Read the current Case overview using its known Investment Case and Decision Cycle IDs, then call `strata_read_calculation_run` with exactly `{ "runId": selectedRunId, "projection": "summary" }`. If only a visible retained Run ID is known, read that summary first to obtain the Case and Cycle IDs, read the current Case overview, then refresh the same Run summary before preview. Reads need no confirmation. Require summary `status: "successful"` and exact agreement of its Investment Case, Decision Cycle, and Case Revision IDs with the fresh Case. If the Run is missing, inaccessible, unsuccessful, or for another revision, stop without a calculated preview or write. Explain only returned facts and ask the user to select another Run when needed. Do not silently substitute a Run or change the requested reliance to non-calculated.

If a calculated Decision returns `STALE_STATE`, make no second mutation in that turn. Refresh both the current Case overview and the exact selected Run summary. If the Case head changed, the old Run cannot support a Decision over the new revision. Preserve the failed intent and stop until the user explicitly selects a retained successful Run for the new revision. Read the current Case and exact replacement Run summary before a complete changed preview. Obtain a separate confirmation and use a new key. If the Case head did not change, stop. Keep the ambiguous-response same-key replay rule unchanged.

Keep the user's outcome, selected Option and optional Scenario, rationale, Conditions, disagreements, and complete Outcome Commitments separate from Run selection. Result ordering does not select an outcome. Clarify any missing user choice. Preview the complete `strata_create_decision` input without `idempotencyKey`, using the current Case Revision for both revision fields and exactly `{ "reliesOnCalculatedResults": true, "calculationRunId": selectedRunId }` for `calculation`. State that reliance covers the whole successful Run, not a result, group, or comparison. After explicit confirmation, add only a new version 4 UUID key and call once. For a non-calculated Decision set `calculation.reliesOnCalculatedResults` to `false`. Never imply that a calculation occurred without a successful exact Run. Approve and pilot Decisions require one selected Option Revision and at least one Outcome Commitment. Reject, defer, and stop may omit Commitments. Copy every Commitment `accountableUserId` only from authorized Uprali output that identifies the member selected by the user, such as a returned current Case revision author or member ID. Never convert a WorkOS ID or invent a user ID. If the selected member cannot be bound to a returned internal member ID, stop and explain that current MCP output cannot identify that member.

When `strata_export_calculation_model` is available and the user asks for a Run's model as a file, call it with the exact `runId` of a Run that `strata_create_calculation_run` or `strata_read_calculation_run` returned and the requested `format`, `csv` or `xlsx`. In a host that shows the workspace App, the result also opens an export view. When the result has `downloadUrl`, give it to the user as a link named with the returned `fileName` and tell the user to open the link to download the file; the link expires 15 minutes after the export. Do not write the file, attach it, or give its content as a code block. When the result has no `downloadUrl`, attach the export to the chat as a file named with the returned `fileName`: write CSV `content` into a `.csv` file, or decode XLSX `contentBase64` into an `.xlsx` file. Tell the user to download the attached file. When the host gives you no way to create a file, give CSV `content` as a code block; for XLSX, say that you cannot attach the file and offer a CSV export. Do not edit, recompute, or summarize values beyond what the export returned. When the tool is not available, say that model export is not available.

When `strata_read_calculation_results` is available and the user asks to see a Run's results, call it with the Run's exact `runId`; the App shows the results view.

When `strata_read_success_metrics` is available, read the case's success metrics before previewing an approve or pilot Decision and offer them as starting points for Outcome Commitments. Take every Commitment field from the user's confirmation; a success metric alone never creates a Commitment.

Use the current overview's `caseReference.caseRevisionId` for both `caseRevisionId` and `expectedCaseRevisionId`. Map its matching `alternativeRevisionId` to `selectedOptionRevisionId` for a selected Option and use it directly for an option disagreement. The overview does not return Scenario IDs. For a selected Scenario or scenario disagreement that is not already fresh, call the scenario projection with a stable `scenarioId` already returned by Uprali and pin it to the same current Case Revision. Map the returned `scenarioRevisionId` to `selectedScenarioRevisionId` for a selected Scenario or use it directly for a scenario disagreement. For assumption disagreements, read the assumptions projection against that Revision and use its returned `assumptionRevisionId`. If a required stable ID or current Revision is unavailable, stop.

On create `STALE_STATE`, reread the current overview. If the Case head changed, compare the proposed Decision with the returned current state, show a complete new preview, obtain new confirmation, and use a new key. If the reread returns the same Case head, stop because the Cycle may already contain a Decision and the current MCP tools cannot safely identify or recreate it.

Use `strata_read_decision` to read a currently authorized immutable Decision by `decisionId`. Output returns the exact Case Revision, outcome, rationale, selected revisions, non-calculated declaration, Conditions, disagreements, and Commitments.

When `strata_read_approval_path` is available and the user asks for a case's Decision or Outcome Review without a visible ID, resolve the case and call `strata_read_approval_path` with its exact `investmentCaseId`. Pass the returned `decisionId` to `strata_read_decision`. Pass the returned `outcomeReviewReference` unchanged as `reference` to `strata_read_outcome_review`. When either value is `null`, state that the case has no Decision or no Outcome Review. When `strata_read_approval_path` is not available, this rule does not apply.

## Outcome Review and Learning

Use `strata_save_outcome_review_revision` to author a root or corrective Review Revision. For a new Review, send `review.kind: "new_review"` and `assessmentDate`. For a correction, send `review.kind: "correction"`, `outcomeReviewId`, and `expectedCurrentRevisionId`. Include the complete authored Observation set for this Revision; this set may omit due Observations while the Revision remains a draft. Include optional Learnings, `decisionId`, `changeReason`, and `idempotencyKey`. For every `learnings[].succession`, perform a fresh `strata_read_learning` of its `predecessorLearningId` and continue only when the predecessor lifecycle is `accepted`, not `draft`, `retired`, or `superseded`. Effect: closed-world idempotent write. Output: `decisionId`, `outcomeReviewId`, `outcomeReviewRevisionId`, `revisionNumber`, `assessmentDate`, `decisionLearningIds`, `recordedAt`, and `replayed`.

For save `VALUE_INCOMPATIBLE`, compare the proposed complete Revision with the fresh Decision. For a rejected `new_review` save, no Outcome Review exists to read. For a correction, also compare the proposed Revision with the fresh current Outcome Review. Correct only the evidenced Observation-to-Commitment or Learning-support discrepancy; otherwise stop. Show a complete corrected preview and obtain new confirmation before retrying with a new idempotency key.

Use `strata_complete_outcome_review_revision` only after two fresh reads confirm the exact current Revision is ready. Read the current Outcome Review by `outcomeReviewId`. If the starting read used a historical `review_revision` reference, use its returned `outcomeReviewId` for that current read. Use the current Review's returned `decisionId` for `strata_read_decision`. Map each Decision `commitments` array index to `outcomeCommitmentPosition` and select every Commitment whose `reviewDate` is on or before the Review `assessmentDate`, and only those. Confirm that the current Revision has exactly one Observation for every due position and no other positions. Compare each Observation's `actualResult` kind with the corresponding Commitment `expectedResult`: for `numeric` or `numeric_range` results the `unitKey` must match, and for `money` or `money_range` results the `currencyCode` must match. An Outcome Commitment (`strata_create_decision`) and an Outcome Observation (`strata_save_outcome_review_revision`) both carry the authored money form `{ "kind": "money", "amount": "<decimal in major unit>", "currencyCode": "<supported code>" }` (or the authored `money_range` lower/upper decimals with bounds), while reads return the realized `{ "kind": "money", "amountCents": "<integer smallest-unit amount>", "currencyCode": "<supported code>" }`; never send a realized field. Send only a currency code the tool schema publishes: the schema carries the supported-code enum, and a code outside that set is rejected. Preview completion only after both fresh reads agree. Copy the current `outcomeReviewRevisionId` as `expectedCurrentRevisionId`.

Input: `decisionId`, `outcomeReviewId`, `expectedCurrentRevisionId`, and `idempotencyKey`. Effect: closed-world idempotent write that completes the Revision and accepts its Learnings. Output: `decisionId`, `outcomeReviewId`, `outcomeReviewRevisionId`, `acceptedDecisionLearningIds`, `completedAt`, and `replayed`. A due-Observation set or result kind, unit, or currency mismatch returns `VALUE_INCOMPATIBLE`, not `STALE_STATE`. `STALE_STATE` means the Review Revision changed, is no longer current, is already completed, or its Learning predecessor state changed. Malformed inputs return `INPUT_INVALID`.

On completion `VALUE_INCOMPATIBLE`, compare the fresh Decision and current Outcome Review and identify the exact mismatch. Separately preview and confirm a complete corrective Review Revision, save it with a new key, and reread the Review. Show a new completion preview and obtain new confirmation before completing the corrected current Revision with another new key. If no evidenced correction can be prepared, stop.

Use `strata_read_outcome_review` with exactly one top-level `reference`: `reference: { kind: "review", outcomeReviewId }` for a current read or `reference: { kind: "review_revision", outcomeReviewRevisionId }` for an exact historical read. Include `limit: 1`, and use a returned cursor only with the same `reference`. Output returns the protected current or historical Revision, its Observations, Learnings, completion state, exact Case Revision, and `nextCursor` when another Revision page exists.

Use `strata_read_learning` with `decisionLearningId`, `limit`, and returned cursor only for the same Learning. Output returns protected Learning content, source Review Revision, Observations, lifecycle, `sourceStatus`, target summary, bounded explicit references, and `nextCursor`. `sourceStatus: "outdated"` means the supporting Outcome Review Revision has a completed correction; it does not retire, supersede, alter, or invalidate existing references.

Use `strata_retire_learning` only after the user confirms retirement of one accepted Learning. Input: `decisionLearningId`, `expectedStatus: "accepted"`, `reason`, and `idempotencyKey`. Effect: destructive idempotent write. It appends retirement and never deletes Learning content or existing references. Output: `decisionLearningId`, `retiredAt`, and `replayed`. A retired, superseded, draft, or otherwise non-accepted Learning returns `STALE_STATE`. For Learning retirement, `CASE_NOT_FOUND` means the Learning is missing or inaccessible. Stop without inference, alternate-ID probing, or hidden-relationship disclosure.

## Exact Learning References

Use `strata_revise_case_learning_references` to author the complete selected Learning reference set on a successor Case Revision. Input: `investmentCaseId`, `decisionCycleId`, `expectedCaseRevisionId`, `references`, `changeReason`, and `idempotencyKey`. Each reference has `decisionLearningId`, `reuseReason`, and `applicabilityExplanation`. Effect: closed-world idempotent Case Revision write. Output includes `operation: "case.learning_references.revised"`, `caseRevisionId`, `caseRevisionNumber`, `caseKey`, `investmentCaseId`, `decisionCycleId`, `authorUserId`, `recordedAt`, `changeReason`, `provenance`, `referenceCount`, `idempotencyKey`, and `replayed`.

Because `strata_revise_case_learning_references` replaces the complete Case Learning reference set, use it only when authorized Uprali output in the current conversation contains the complete current set for the same exact `expectedCaseRevisionId`. No Case projection guarantees the complete current Case Learning reference set. The authorized output must show every page or prove that no later page exists. If the complete current set is unavailable, stale, or paginated beyond the returned output, stop and ask the user to use a Uprali surface that can show it before this plugin writes. Do not add one Learning to an unknown set. `strata_read_learning` returns target summary counts, not the complete Case Learning reference set.

Use `strata_publish_template_learning_references` to publish one successor Template Revision with the complete selected Learning reference set. Input: `expectedTemplatePublicationId`, `references`, `changeReason`, and `idempotencyKey`. Protected Uprali output in the current conversation must supply both the current `caseTemplatePublicationId` and the complete current Template Learning reference set. The current exposed tool set does not include a separate Template Publication read. If either value is absent or the set is partial, stop and ask the user to use a Uprali surface that can show both before this plugin writes. Perform a fresh `strata_read_learning` for every Learning in the proposed successor set and continue only when each lifecycle is `accepted`, not `draft`, `retired`, or `superseded`. After `STALE_STATE` or `COMMAND_REUSED`, proceed only if a Uprali surface supplies a fresh current Template Publication ID and a fresh complete current Template Learning reference set. Otherwise stop. Never mutate an unknown or partial Template Learning reference set. Effect: closed-world idempotent Template Revision and Publication write. Output: `caseTemplateId`, `caseTemplateRevisionId`, `caseTemplatePublicationId`, `revisionNumber`, `publishedAt`, `referenceCount`, and `replayed`.

Do not attach Learning references retrospectively. Do not reference a retired or superseded Learning. A reference to an outdated-source Learning requires a nonblank applicability explanation that explains why it remains applicable. Use a Case or Template exact revision reference, not only a stable Case, Investment Case, or Template identity.
