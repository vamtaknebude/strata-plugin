# History and comparison

- Use `strata_list_case_revisions` when the user asks for revision history or needs a revision selected by recorded operation, author, or time. Preserve its cursor for further history pages.
- Interpret “previous” as the selected revision's exact `parentCaseRevisionId`, never the second item in a date-sorted list.
- Use `strata_compare_case_revisions` only with two exact revision IDs and `limit: 25`. Set `fromCaseRevisionId` to the older/base revision and `toCaseRevisionId` to the newer/target revision.
- For “what changed since the previous revision,” use the selected current overview's `parentCaseRevisionId` immediately as `fromCaseRevisionId` and its `caseRevisionId` as `toCaseRevisionId`. The complete normal sequence is bounded case list, current overview, then exact comparison. Do not call `strata_list_case_revisions`, because history order is not the parent relation. Do not read the parent overview unless the user explicitly asks for a previous value that the comparison does not return.
- Report every returned comparison item. For a narrative item, name every entry in `changedFields`, even when several fields changed in one item. Pair each changed field with its current value from the already returned overview when that field is present there; for example, report the current objective text and current deadline, not only “objective and deadline changed.” For subject items, preserve `added`, `changed`, and `removed` exactly. Fetch another exact projection only if the user's question requires a subject's actual value that the comparison and current overview do not return.
- Do not describe a change as causal. Revision lineage establishes author, recorded time, and change reason, not business causation or objective truth.

## Scenario compared with Base

When `strata_compare_scenario_to_base` is available and the user asks to compare a named scenario with Base, skip Read workflow steps 3 to 8. Take `runId` and `option.optionRevisionId` from this case's latest `strata_read_calculation_results` result; if there is none, resolve the case and call that tool with its `investmentCaseId`. Then call `strata_compare_scenario_to_base` once with `scenarioLabel` set to the user's scenario name and `limit: 25`, and answer with its Pairwise Results, such as NPV and payback.

- For a retained Counterfactual comparison, read the exact Run with `strata_read_calculation_run` using `{"runId":"<exact Run UUID>","projection":"comparison","optionRevisionId":"<proposed Option Revision UUID>","scenarioRevisionId":"<Scenario Revision UUID>","limit":25}`. Use a smaller valid limit when the user requests it. On each next page, copy `page.nextCursor` into `cursor` without interpreting it and retain the other selectors. Absence of `nextCursor`, not `returnedCount < limit`, ends traversal: a byte-limited page can contain fewer members than requested and still have a continuation. Present each complete member once; do not skip an index or drop the first member of the next page.
- For comparisons, preserve `proposedOutcome`, `counterfactualOutcome`, and each Pairwise `outcome`. The reads return every identity the summary needs: each response echoes `runId`, `optionRevisionId`, and `scenarioRevisionId`, and returns `counterfactualOptionRevisionId` alongside them. Copy all four IDs character-for-character from the returned reads, never from memory, and never truncate or abbreviate one. Begin the final summary with these four sentences in this order, with each exact ID filled in, before any outcome: The retained Run is <runId>. The proposed Option Revision is <optionRevisionId>. The Counterfactual Option Revision is <counterfactualOptionRevisionId>. The Scenario Revision is <scenarioRevisionId>. The tool-call record does not substitute for these sentences: before finishing, check that each full ID appears in the summary and add any missing sentence. Preserve scalar kind, unit, and currency, series period order, and failure diagnostic fields. A failed member has no calculated value while independent successful members remain inspectable. Do not convert a failure to zero or infer a missing value.
- On a retained comparison read error, state the returned diagnostic and which exact request failed. Do not retry with a different Run or revision, and do not claim completion after partial traversal. Ordinary read calls need no confirmation. A comparison explanation issues no writes and makes no Option recommendation.
- For a retained ordered Result Group, read the exact Run with `strata_read_calculation_run` using `{"runId":"<exact Run UUID>","projection":"result_group","optionRevisionId":"<proposed Option Revision UUID>","scenarioRevisionId":"<Scenario Revision UUID>","resultGroupKey":"<exact key>","limit":25}`. The same cursor rules apply: copy `page.nextCursor` into `cursor` unchanged, and traverse until `nextCursor` is absent.
- For groups, preserve the received `members` order exactly, including a successor Model that reverses the order or changes the title: open the summary by stating the exact `runId`, `optionRevisionId`, `scenarioRevisionId`, returned `counterfactualOptionRevisionId`, historical `modelRevisionId`, group key, and title, never current Model order. Distinguish `comparison_result` members by (`modelItemKey`, `side`) and Pairwise members by `pairwiseResultKey`. Do not derive group membership from comparison output and do not sort by label or key. A failed member has no calculated value while independent successful members remain inspectable. A group explanation issues no writes and makes no Option recommendation.
